八、真正的有价值问题

综合两份报告和代码审查，以下是经过验证的10 个真实存在的问题：

P1: Extent 分配器的分布式一致性 高优先级

来源：GLM5.2 #27模块：engine/extent.rs + control/server.rs

当前 LargeObjectRegion 的 free-list 和 bump 分配是服务端本地操作。分布式 RDMA 模式下，Server 的 extent 分配状态变化时 Client 无法感知。gRPC 控制面只分发 初始 MR 元数据，不实时同步 extent 分配状态。control/server.rs 中注释 "Set by actual MR registration in distributed mode" 印证此问题。

P2: 缺乏 Slab 分配器 / vLLM Block Size 对齐 中优先级

来源：GLM5.2 #33模块：engine/extent.rs

变长 extent 分配器与 vLLM 的固定大小 KV Block（16 token × hidden_dim × dtype_size）不匹配。变长分配导致碎片且无法利用定长块优势。需要 Slab 分配器或 Chunk 大小对齐。

P3: GPUDirect RDMA (GDR) 缺失 中优先级

来源：GLM5.2 #34模块：transport/rdma.rs

远端 KV Cache 数据先到 CPU 内存再 cudaMemcpy 到 GPU 显存，额外 PCIe 往返增加 ~10-30μs 延迟。设计文档中规划但未在代码中实现。

P4: PCIe 带宽竞争 中优先级

来源：GLM5.2 #31层面：系统架构

当 Server 节点同时运行推理（GPU→PCIe）和 RDMA（NIC DMA→PCIe），两者共享 PCIe 带宽。推荐存储节点与计算节点物理分离。

P5: 无 QP 错误状态自动恢复 中优先级

来源：QWEN #18模块：rdma/qp.rs

QP 进入 ERROR 状态后无显式自动恢复（检测 ERROR→销毁+重建 QP→重建连接）。生产环境中可能导致连接永久失效。

P6: 无 LRU 缓存淘汰策略 中优先级

来源：GLM5.2 #23模块：engine/gc.rs

仅 EpochGc 处理 tombstone 回收，无缓存淘汰（LRU/LFU）。作为 LMCache L2 后端，内存满时需淘汰冷数据。KvEngine trait 不含淘汰接口。

P7: 数据撕裂风险（Extent 大对象） 中优先级

来源：GLM5.2 #30模块：engine/concurrency.rs

大对象的 RDMA WRITE 非原子。乐观读协议（前后版本号校验）是检测而非预防。极端情况可能读到部分写入。

P8: CQ 异步事件处理缺失 低优先级

来源：QWEN #19模块：rdma/cq.rs

仅 busy-poll 模式，无 CQ overrun 检测或 ibv_get_async_event 处理。

P9: PFC/ECN 部署文档缺失 低优先级

来源：QWEN #12层面：运维文档

生产级 RoCE 流控配置指南缺失。README 覆盖了 SoftRoCE 但无 PFC/ECN 细节。

P10: 传输层加密 低优先级

来源：两份报告层面：安全

数据面无加密。RDMA 可信内网标准做法，多租户云环境可能成为合规要求。

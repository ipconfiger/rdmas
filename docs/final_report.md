## 四、真正的有价值问题

综合两份报告和代码审查，以下是经过验证的**真实存在的问题**：

### 4.1 架构层面

#### P1: Extent 分配器的分布式一致性
**来源**：GLM5.2 #29 "控制面与数据面边界模糊"
**问题**：当前 `LargeObjectRegion` 的 free-list 和 bump 分配是服务端本地操作。分布式 RDMA 模式下，当 Server 端的 extent 分配状态变化时，Client 如何无冲突地进行 Extent 写入？当前 gRPC 控制面只分发初始 MR 元数据，不实时同步 extent 分配状态。
**严重性**：高——这是分布式模式下核心功能完整性的阻碍。
**当前状态**：代码在 `control/server.rs` 中注释 "Set by actual MR registration in distributed mode"，表明分布式 extent 分配尚未实现。

#### P2: 缺乏 Slab 分配器与 vLLM Block Size 对齐
**来源**：GLM5.2 #35 "Block Size 粒度"
**问题**：`LargeObjectRegion` 的变长 extent 分配器（free-list + bump）与 vLLM 的固定大小 KV Block（通常 16 token × hidden_dim × dtype_size）之间存在不匹配。变长分配导致内存碎片，且无法利用定长块的优势（如预计算偏移）。
**严重性**：中——不影响核心功能，但影响 LMCache 集成效率和内存利用率。
**当前状态**：未实现。

#### P3: GPUDirect RDMA (GDR) 缺失
**来源**：GLM5.2 #36 "GPUDirect RDMA 缺失"
**问题**：在 vLLM 推理场景中，从远端读取的 KV Cache 数据先到 CPU 内存，再通过 `cudaMemcpy` 到 GPU 显存。这一步是额外的 PCIe 往返，增加 ~10-30μs 延迟。
**严重性**：中高——对延迟敏感的 LMCache L2 场景是显著瓶颈，但需要特定硬件支持（NVIDIA GPUDirect-capable 网卡）。
**当前状态**：设计文档中提及但未在代码中实现。`src/transport/rdma.rs` 的 read/write 方法接收的是 CPU 内存缓冲区。

#### P4: PCIe 带宽竞争
**来源**：GLM5.2 #33 "PCIe 带宽竞争"
**问题**：当 Server 节点同时运行推理（GPU 使用 PCIe）和 RDMA（网卡 DMA 使用 PCIe）时，两者共享 PCIe 带宽。
**严重性**：中——属于系统架构级考量，RDMA 项目通常不负责解决。
**当前状态**：代码未涉及。推荐在生产部署中将存储节点与计算节点物理分离。

### 4.2 实现层面

#### P5: 无 QP 错误状态自动恢复
**来源**：QWEN #19 "QP 错误状态处理缺失"
**问题**：当 QP 因网络故障进入 ERROR 状态后，代码无显式的自动恢复机制（检测 ERROR → 销毁并重建 QP → 重新建立连接）。
**严重性**：中——在网络不稳定的生产环境中可能导致连接永久失效。
**当前状态**：代码检查各操作的返回值但在 QP 级别无状态机监控。

#### P6: CQ 异步事件处理缺失
**来源**：QWEN #20 "CQ 溢出处理缺失"
**问题**：代码使用 busy-poll 模式，无 CQ overrun 检测或无 `ibv_get_async_event` 处理。在高负载或 CQ 尺寸不足时可能丢失完成事件。
**严重性**：中低——在适当配置 CQ 大小的测试环境中不触发，但在生产高负载下是风险。
**当前状态**：CQ 通过 `cq.poll(16)` 轮询，但无异步事件通道。

#### P7: 无 LRU / 缓存淘汰策略
**来源**：GLM5.2 #25 "生命周期管理偏简单"
**问题**：`EpochGc` 仅处理 tombstone 回收（基于最小活跃时间戳的 epoch 驱逐），但无缓存淘汰策略（如 LRU、LFU）。作为 LMCache L2 后端，内存满时需要淘汰冷数据。
**严重性**：中——LMCache 在其 L1 层有淘汰逻辑，L2 层可能需要配合。
**当前状态**：`KvEngine` trait 不含淘汰接口。`src/engine/gc.rs` 只做 tombstone 回收。

#### P8: 无 PFC/ECN 网络部署文档
**来源**：QWEN #13 "RoCE 流控配置缺失"
**问题**：RoCE 需要 PFC 和 ECN 实现无损网络。项目未提供这些配置指南。
**严重性**：低——属于运维文档范畴，不影响代码质量。但缺少这些指南会导致首次部署者遇到性能问题。
**当前状态**：README 覆盖了基本的硬件和 SoftRoCE 配置，但无生产级 RoCE 流控指导。

#### P9: 无传输层加密
**来源**：两份报告均有提及
**问题**：数据面 RDMA 流量无加密。
**严重性**：低——RDMA 系统通常在可信数据中心内网运行。但在多租户或云环境中可能成为合规要求。
**当前状态**：未实现。标准 RDMA 实践。

#### P10: 数据撕裂风险（Extent 大对象）
**来源**：GLM5.2 #32 "数据撕裂"
**问题**：大对象（MB 级）的 RDMA WRITE 不是原子的。当前代码通过乐观读（前后版本号校验）应对，但这是在 Client 端的检测而非预防。极端情况下可能读到部分写入的数据。
**严重性**：中——当前有缓解措施（版本号校验），但未从协议层面消除风险（如两阶段写入）。
**当前状态**：乐观读协议在 `concurrency.rs` 中实现。这是 RDMA 系统的标准做法。

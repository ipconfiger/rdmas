# Rust RDMA KV 存储：多波次开发执行计划

> 配套 `Rust-RDMA.md`（v3 正式方案）的工程落地计划。
> 采用**波次（Wave）+ 并行轨道（Track）+ 关卡门禁（Gate）**结构：同一波次内的轨道可并行推进，跨波次由关卡门禁严格约束，未过门禁不进入下一波。

---

## 执行模型说明

- **波次（Wave）**：一个时间盒（1–2 周），结束时必须通过**关卡门禁（Gate）**方可解锁下一波。
- **轨道（Track）**：波次内可并行的独立工作单元。同一波次的轨道**写作用域不重叠**，可分配给不同开发者/Agent 并行。
- **关卡门禁（Gate）**：客观可验证的通过标准（测试通过、指标达成、风险清除）。
- **风险卡点（Risk Check）**：前置高风险项，必须在波次早期消除，否则触发降级预案。

**全程两条铁律：**
1. **TDD**：生产代码先写测试再写实现（测试代码可放宽 `unwrap`/`any`）。
2. **改后必验**：任何编译型改动必须 `cargo build` + `cargo test` 通过，禁止假设正确。

## 🌊 Wave 1 — 基础设施奠基（第 1–2 周）

**波次目标：** 打通 Safe Rust ↔ RDMA 硬件的通路，并**优先清除最高风险（硬件 CAS）**。

| 轨道 | 职责 | 写作用域 | 可并行 |
|------|------|----------|--------|
| **T1-A FFI 封装层** | 基于 `rdma-sys` 封装 `Context`/`ProtectionDomain`/`MemoryRegion`/`QueuePair`/`CompletionQueue`，**包含 QP 状态机（INIT→RTR→RTS）管理及连接拆除/重连逻辑**；`Drop` 自动 `ibv_dereg_mr`/`ibv_destroy_*` | `src/rdma/` | ✅ |
| **T1-B HugePages 分配器** | `mmap` 2MB/1GB 大页 + 自动注册 MR + RAII 资源清理 | `src/mem/` | ✅ |
| **T1-C 异步运行时骨架** | busy-poll 轮询线程（绑核）+ `crossbeam` 无锁 channel + `oneshot` 唤醒 `Future`；提供 `async fn rdma_read/write` | `src/runtime/` | ✅（依赖 T1-A 接口，可先用 mock 并行） |
| **T1-D 🔴 硬件 CAS 验证** | 独立 bench：测网卡 `RDMA_CMP_SWAP` 延迟/IOPS，判定是否支持 | `benches/cas/` | ✅ **最高优先，Day 1 启动** |

**🔴 风险卡点（Wave 1 Day 3 前）：** T1-D 验证 CAS。
- **达标定义**：RDMA CAS 延迟 ≤ 2× RDMA READ 延迟 AND CAS IOPS ≥ 50% RDMA WRITE IOPS（目标硬件实测）。任一不满足 → 触发降级预案。
- 若网卡 CAS 性能达标 → 继续 One-Sided 路线。
- **若不达标** → 触发降级预案：Two-Sided Send/Recv + Server CPU 介入（牺牲 One-Sided，保可用），同步调整后续波次设计。

**关卡门禁 Gate-1：**
- [ ] 两台机器（或同机双进程）完成一次异步 `RDMA_READ`/`WRITE` 乒乓，数据正确。
- [ ] `Drop` 资源清理验证：反复创建销毁 MR/QP 无句柄泄漏（`ibv_devinfo`/valgrind）。
- [ ] CAS bench 报告产出，路线决策落地。

## 🌊 Wave 2 — 本地内存引擎（第 3–4 周）

**波次目标：** 不联网，纯本地实现 Cuckoo Hashing + CAS 并发，用 `unsafe` 指针模拟远端内存访问，把数据结构与并发逻辑跑通。**v3：布局支持双模（Inline 小值 / Extent 大对象）。**

| 轨道 | 职责 | 写作用域 | 可并行 |
|------|------|----------|--------|
| **T2-A 双模数据结构** | `HashBucket`（Inline/Extent 双模）+ `ExtentHeader`：`#[repr(C, align(64))]` + `Pod` + **编译期静态断言**（size==64, align==64） | `src/engine/layout.rs` | ✅ |
| **T2-B Cuckoo Hashing 核心** | 插入/查找/删除/踢出（`MAX_KICK=16` 防活锁）；本地指针解引用版本；双模分发 | `src/engine/cuckoo.rs` | ✅（依赖 T2-A 类型，接口先行） |
| **T2-C 无锁并发控制** | 本地 CAS 锁 + 租约时间戳 + version 单调递增 + 乐观读校验 | `src/engine/concurrency.rs` | ✅ |
| **T2-D 大对象区与分配器** | Large Object Region（extent-based）+ extent 分配器/无锁 Free List；为 LMCache KV cache 张量准备 | `src/engine/extent.rs` | ✅ |
| **T2-F 引擎初始化** | Server 侧引擎 bootstrap：HugePages 上布局 Hash Table（桶清零）、Large Object Region、Free List Region，初始化 Free List，暴露区域边界供 T3-A 广播 | `src/engine/bootstrap.rs` | ✅（依赖 T2-A 布局定义） |
| **T2-E 单元/压力测试** | 多线程并发 100 万 KV（小值 Inline + 大值 Extent 混合）；`loom` 模拟并发；内存泄漏检测 | `tests/engine/` | ⬜ 依赖 A/B/C/D/F |

> **Week 2 Day 1 里程碑：** T2-A 类型定义 + T2-B Cuckoo API + T2-C 并发原语 API 三者接口对齐，联合设计会议产出以下契约：
> - `HashBucket` 公开方法（`is_empty`, `matches_key`, `extract_value`, `write_inline` 等）
> - `LockGuard` / `ReadSnapshot` 类型与 `try_acquire` / `release` / `validate` 签名
> - Cuckoo 插入/查找/删除/踢出对并发原语的调用点
> 未对齐前不开始并行编码。

**关卡门禁 Gate-2：**
- [ ] 多线程并发插查 100 万 KV（Inline + Extent 混合负载），数据一致（无丢失/无错配）。
- [ ] 无数据竞争（MIRI / ThreadSanitizer 覆盖所有 T2-E 并发测试用例：100 万 KV 并发插入/查找/删除，Extent 分配/回收竞态，踢出链并发）。
- [ ] 无内存泄漏（长跑压力测试内存平稳）。
- [ ] 踢出链达到 `MAX_KICK` 时正确返回 `KV_FULL`，无活锁。
- [ ] Extent 分配/回收正确，大对象单次读取完整。
- [ ] 哈希表负载因子 > 50% 时插入返回 `KV_FULL`（而非活锁或无限重试），行为可预测。

## 🌊 Wave 3 — 分布式数据面打通（第 5–7 周）

**波次目标：** 把 Wave 2 的本地指针/原子操作，**语义映射**为真实 One-Sided RDMA 操作（注意：本地 AtomicU64 的 CPU 内存模型与 RDMA CAS 的远端原子语义不等价，需额外处理内存序与网络部分失败），打通多 Client 并发。

| 轨道 | 职责 | 写作用域 | 依赖 |
|------|------|----------|------|
| **T3-A 控制面** | gRPC/Tonic：Server 注册 MR → 广播 `rkey`+`vaddr` 给 Client；心跳/节点发现 | `src/control/` | — |
| **T3-B Client 读路径** | 指针解引用 → `rdma_read`；Inline 命中 1 RTT，否则探 B2 / Extent 整块 READ | `src/client/read.rs` | T3-A |
| **T3-C Client 写路径** | 本地原子 → `rdma_cas`；实现四步踢出状态机（锁→搬→写→解）+ 读侧重试协议 | `src/client/write.rs` | T3-A |
| **T3-D 异常与重试** | 超时/传输错误重试；乐观读 version 不一致重试；`PendingTracker` 超时兜底回收 Buffer | `src/client/retry.rs` | T3-B/C |
| **T3-E Client 生命周期** | Client 加入/离开协议：发现 Server → 获取 MR 元数据 → 建立 QP → 心跳维持 → QP 错误检测与重连 → 崩溃重启后重建状态 | `src/client/session.rs` | T3-A |

**关卡门禁 Gate-3：**
- [ ] 多 Client 节点并发读写同一 Server，数据线性一致（一致性测试套件通过）。
- [ ] **Server 数据面 CPU 占用 = 0%**（`perf stat` 实测：60 秒饱和负载下，Server 数据面内存访问函数（读/写路径）采样数为 0；GC/控制面/复制线程 CPU 不计入。目标：Server CPU 不处理任何数据面中断或轮询）。
- [ ] Cuckoo 踢出在并发下无数据损坏（读写交叉压力测试）。
- [ ] Extent 大对象跨节点 READ 正确（LMCache 负载预演）。

## 🌊 Wave 4 — 容错、GC 与尾延迟优化（第 8–9 周）

**波次目标：** 补齐工程"坑"，达到生产级可用。**可与 Wave 5 并行**（写作用域不重叠：本波次在 `src/engine`、`src/control`，Wave 5 在独立 crate）。**前提：引擎核心在 Gate-3 时暴露稳定公开 Trait（KvEngine），Wave 5 代码仅依赖此 Trait。Wave 4 修改引擎内部实现时禁止破坏公开 Trait 契约。**

| 轨道 | 职责 | 写作用域 | 可并行 |
|------|------|----------|--------|
| **T4-A 租约过期接管** | CAS 锁过期检测 + 强制接管 + 结构修复（防 Client 崩溃死锁） | `src/engine/concurrency.rs`（扩展） | ✅（编码可并行，但测试需 Gate-3 通过的分布式环境） |
| **T4-B 去中心化 Epoch GC** | Client 维护 `active_ts`；Server 控制面收集 `min(active_ts)`；回收死亡 Extent 归还 Free List；**同时清理 tombstone 桶（CAS 置零，释放哈希表槽位）** | `src/engine/gc.rs` | ✅ |
| **T4-C 性能优化** | Inline Data 优化（<32B 单 RTT）；SGE 批量 `post_send`；轮询线程调优。**启动前提：需先完成 Gate-3 性能基线测量，基于 hotspot 分析选择优化方向。** | `src/client/opt.rs` | ✅ |
| **T4-D 容错备份** | 后台异步 RDMA WRITE 复制到备份节点（或 NVMe-oF 持久化） | `src/control/replication.rs` | ✅ |

**关卡门禁 Gate-4：**
- [ ] **24 小时高压稳定性测试**（80% 峰值吞吐，50/50 读写比，Zipfian 分布 Key，20% Extent / 80% Inline value，持续 24h）：无死锁、无内存耗尽、无句柄泄漏。
- [ ] 模拟 Client 崩溃后，锁被租约过期正确接管，系统自愈。
- [ ] GC 正确回收已删 Extent，无悬挂指针 / 无重复分配。
- [ ] **尾延迟 P99 < 10μs**。

## 🌊 Wave 5 — LMCache L2 适配层（第 9–10 周，可与 Wave 4 并行）

**波次目标：** 让本引擎作为 LMCache 的可配置 L2 存储引擎接入，端到端跑通 vLLM+LMCache 的 KV cache 存取。

> 依赖：仅需 **Gate-3**（分布式数据面）通过即可启动，与 Wave 4 并行。写作用域为独立 crate，不与 Wave 4 冲突。
> 参考：LMCache 官方 `rust/raw_block`（PyO3 cdylib）、`csrc/storage_backends/fs/connector.cpp`、`examples/lmc_external_native_connector/`。锁定 LMCache commit `9c0bcd8`。

| 轨道 | 职责 | 写作用域 | 依赖 |
|------|------|----------|------|
| **T5-A PyO3 Connector crate** | 独立 `cdylib` crate：`RDMANativeConnector` 类，实现 6 方法骨架（`event_fd`/`submit_batch_get/set/exists/delete`/`drain_completions`/`close`）；`pyo3-stub-gen` 生成类型存根 | `crates/lmcache-connector/` | Gate-3 |
| **T5-B Worker 线程池 + eventfd** | 镜像 LMCache `ConnectorBase`：N×worker（每 worker 一个 RDMA QP）+ 请求 SQ + 完成 CQ + eventfd 通知；`batch_chunk_num_bytes` 聚合 | `crates/lmcache-connector/worker.rs` | T5-A、T1-C（Runtime）、T3-B（读）、T3-C（写）、T3-D（重试/PendingTracker） |
| **T5-C Key/Value 适配** | LMCache `ObjectKey` 字符串（`model@rank@gid@hash[@salt]`）→ 64-bit hash + 16B digest；value 走 Extent 大对象区；memoryview 零拷贝透传 `void*`（`gil_scoped_release`） | `crates/lmcache-connector/adapter.rs` | T5-A/B、T2-D（Extent 分配器，原 T2-E） |
| **T5-D 端到端集成验证** | `pip install` connector；配置 `--l2-adapter '{"type":"native_plugin",...}'`；vLLM+LMCache 跑通 KV cache 存取；对齐官方 6 方法契约校验 | `tests/lmcache_e2e/` | T5-C |

**关卡门禁 Gate-5：**
- [ ] vLLM + LMCache 端到端：KV cache 写入 L2 → 重启/换请求 → 命中读回，数据正确。
- [ ] **零拷贝验证**：`memoryview` → `void*` 直传，无中间拷贝（perf/strace 确认）。
- [ ] 通过 LMCache `NativeConnectorProtocol` 6 方法契约校验（与官方 `native_plugin_l2_adapter.py` 一致）。
- [ ] `future_id → buffer` 映射无歧义；超时 future 由 `PendingTracker` 兜底回收，无泄漏。

## 🌊 Wave 6 — 性能压测与学术对标（第 11–12 周）

**波次目标：** 产出性能报告，对标业界，覆盖通用 KV 与 LMCache 工作负载。**通用 KV 对标（T6-A/T6-B）在 Gate-4 通过后即可启动，无需等待 Gate-5。**

| 轨道 | 职责 |
|------|------|
| **T6-A 热点分析** | `perf record`/`perf stat` + RDMA 硬件计数器，定位 `poll_cq`/内存拷贝等瓶颈 |
| **T6-B 对标测试** | 通用 KV 对比 Redis / Memcached；LMCache 负载对比官方 `raw_block`/FS 后端 |
| **T6-B' 调参扫描** | 并发连接数、Batch 大小、桶数、`batch_chunk_num_bytes` → 吞吐-延迟曲线 |
| **T6-C 报告产出** | 性能报告：吞吐、P50/P99/P999 延迟、CPU 利用率、LMCache L2 命中延迟、瓶颈分析 |

**关卡门禁 Gate-6（最终）：**
- [ ] **Inline 小 KV 吞吐 ≥ 10M OPS**（<32B value, <16B key, 纯读负载）。
- [ ] **Extent 大对象吞吐 ≥ 90% 线速**（100Gbps 环境下单连接 ≥ 11.25 GB/s，1MB value 纯读）。
- [ ] **单次读延迟 P50 < 5μs**。
- [ ] LMCache L2 命中延迟达标：P50 ≤ 官方 raw_block 后端 P50 × 1.1 AND P99 ≤ 官方 raw_block 后端 P99 × 1.2（相同硬件、相同负载）。
- [ ] 性能对标报告产出，瓶颈与优化方向明确。

## 关键风险登记簿（贯穿全程）

| 风险 | 级别 | 触发波次 | 应对 |
|------|------|----------|------|
| RDMA CAS 硬件不支持/性能差 | 🔴 高 | Wave 1 | 降级 Two-Sided + Server CPU 介入 |
| 异步 Buffer 生命周期（借用检查器冲突） | 🟠 中 | Wave 1/3 | 所有权转移 `Box::into_raw/from_raw` + `PendingTracker` 兜底 |
| **复制延迟/脑裂**：主节点宕机时未复制数据丢失；网络分区导致双主 | 🔴 高 | Wave 4 | 明确可接受丢失窗口（<1s）；控制面多数派仲裁防脑裂；备份宕机降级为无复制模式 |
| Server 误读数据面致缓存一致性 bug | 🟠 中 | Wave 3 | 纪律禁止；必要时 `MAP_UNCACHED`/`clflush` |
| Cuckoo 写尾延迟飙升 | 🟡 中低 | Wave 4 | `MAX_KICK` 上限 + 写热点退避 |
| Client 崩溃死锁 | 🟠 中 | Wave 4 | 租约过期强制接管 |
| **LMCache 接口漂移**（v3）：`native_plugin` 契约随上游版本变化 | 🔴 高 | Wave 5 | 锁定 LMCache git tag；CI 每提交验证兼容性；仅接受新增可选方法，强制方法签名变更须升级适配层 |
| **Extent 碎片化**：长周期分配/回收导致 Large Object Region 外部碎片 | 🔴 高 | Wave 4 | 使用 buddy system 分配器；碎片率 > 30% 告警；Compaction 列后续版本 |
| **网络带宽瓶颈**：Extent 大对象吞吐受线速限制 | 🟠 中 | Wave 6 | Inline 与 Extent 吞吐分开度量；Extent 目标 ≥ 90% 线速 |
| **HugePages 不足**：部署环境大页配置不足 | 🟠 中 | Wave 1 | T1-B 启动时检测可用量，不足时输出明确错误；文档记录最低要求 |

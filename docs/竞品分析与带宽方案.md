## 四、多 NIC 聚合方案

### 4.1 Mooncake 方式：服务端协调

```
Client → Transfer Engine (选路) → NIC0/1/2/3 → Server CPU 分片 → DRAM
```

特点：TE 协议层做拓扑感知、多路径负载均衡、自动故障切换。

### 4.2 RDMAS 方式：客户端并行

One-Sided RDMA 允许客户端直接并发读写服务端内存，无需服务端 CPU 参与分片或路由：

```
Client:
  QP0 → NIC0 → RDMA READ chunk[0]  ──┐
  QP1 → NIC1 → RDMA READ chunk[1]  ──┤ 并行直写 Server
  QP2 → NIC2 → RDMA READ chunk[2]  ──┤ HugePage
  QP3 → NIC3 → RDMA READ chunk[3]  ──┘
```

### 4.3 三种可行技术方案

#### 方案 A: 客户端分片读（推荐，最契合现有架构）

大对象按网卡数分片，Client 多 QP 并发 RDMA READ。

| 优点 | 缺点 |
|------|------|
| Server 零改动（HugePage 单地址空间） | Client 端需 QP 池管理 |
| 线性带宽扩展（N 网卡 = N× 带宽） | 大对象才有效 (< 64KB 不值得分片) |
| 与现有 `post_send_batch` 自然衔接 | 需要 NUMA 感知 QP-网卡绑定 |

**代码改动量**：~200 行
- `src/client/read.rs`：新增 `get_striped` 方法
- `src/client/session.rs`：多 QP 池管理
- `src/runtime/ops.rs`：批量 `rdma_read` 并发等待

**分阶段实现**：
```
Phase 1: Client 多 QP 池 + 大对象分片读
  目标: 2×100Gbps → ~22.5 GB/s

Phase 2: QP-NIC NUMA 绑定 + 内存对齐
  目标: 消除跨 NUMA 开销

Phase 3: 自适应分片策略
  阈值: < 64KB 单 NIC, > 64KB 自动分片
```

#### 方案 B: 哈希表分区

不同桶范围绑定不同网卡。小 KV 也能受益。

| 优点 | 缺点 |
|------|------|
| 小 KV 也能受益 | Server 端需多 MR |
| 无分片重组开销 | 桶迁移复杂 (Rehash) |
| 天然负载均衡 | 控制面需广播多 MR 元数据 |

#### 方案 C: RDMA 多路径 (APM)

IB 的 Automatic Path Migration，硬件层负载均衡。

| 优点 | 缺点 |
|------|------|
| 零应用层改动 | 仅 IB 支持，RoCEv2 有限 |
| 硬件自动故障切换 | 依赖网卡固件和交换机 |

## 五、多机部署带宽模型

### 核心洞察

**Mooncake 的 190 GB/s 是多机总带宽，不是单机。**
RDMAS 在多机部署下，总带宽 = 每台 Server 线速之和，且无需 TE 协调层。

### 多机总带宽对比

```
RDMAS 集群:
  总带宽 = Σ(每台 Server 线速 × 0.9)
  协调损耗 = 0 (纯 Client 并发 RDMA)
  Server CPU = 0

Mooncake Store 集群:
  总带宽 = TE 聚合效率 × Σ(每台 Store 线速)
  协调损耗 = TE 协议 + Store CPU 查询
  Server CPU > 0
```

| 规模 | Mooncake Store | RDMAS (理论) | RDMAS 优势来源 |
|------|---------------|-------------|---------------|
| 4×200Gbps | 87 GB/s (实测) | ~90 GB/s | 无 TE 协议开销 |
| 8×400Gbps | 190 GB/s (实测) | ~360 GB/s | 零 CPU 协调 |
| 16×400Gbps | ~380 GB/s (推估) | ~720 GB/s | 线性 Client 并行 |

### 为什么多机部署下 RDMAS 有结构优势

**原因：One-Sided RDMA 天然去中心化。**

客户端并发读 N 台 Server 时：
- 每台 Server 的 CPU 完全不参与数据搬运
- 带宽 100% 由 PCIe DMA 承载
- 客户端瓶颈在本地 QP 并发数，不在服务端

Mooncake 的 Transfer Engine 需要 CPU 参与协议协商和数据路由，必然有损耗。

### 这不是"追上"的问题，是架构取舍

| | Mooncake | RDMAS |
|--|----------|-------|
| **哲学** | CPU 协调换灵活性 | RDMA 零 CPU 换极致带宽 |
| **适用场景** | 多协议、多层级、异构 | 纯 DRAM、同构、极致性能 |
| **复杂度代价** | 高（TE + Store 多层） | 低（直接 Cuckoo 映射） |

## 六、总结：RDMAS 的利基

不做大而全的推理平台。做一个**轻量、安全、低延迟的 Rust One-Sided RDMA 存储引擎**，专注于 LMCache L2 后端场景。

| 维度 | 策略 |
|------|------|
| **vs Redis** | 延迟 10,000× 优势，吞吐 17× 优势 |
| **vs Mooncake Store** | L2 后端延迟更优，多机带宽更优（理论） |
| **多 NIC 聚合** | 方案 A（客户端分片读）可追平单机差距 |
| **生产成熟度** | Wave 7 硬件实测是唯一出路 |

**核心竞争壁垒**：Rust 内存安全 + Cuckoo 确定性延迟 + One-Sided RDMA 零 CPU。这是 Mooncake 的 C++ 多协议架构难以复制的组合。
